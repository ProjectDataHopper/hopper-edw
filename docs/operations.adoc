Day-to-day operation of Data Hopper EDW loads: environments, Docker runners, batch orchestration, and partial model updates.

How you *got* the models and the resource definition group is design-time — see link:architecture.adoc#d4-build-vs-run[Architecture — build vs run] and link:getting-started-edw.adoc[Getting started — building an EDW]. This page is the operate lane.

For **multi-team programs** (who owns core vs subject models, catalog contracts, git vs runtime, analyst discovery), see link:enterprise-modeling-and-team-collaboration.adoc[Organizing large Data Vault programs].

== Docker runners

From the repository root:

[source,bash]
----
# PostgreSQL on port 54320
./scripts/run-postgres.sh up

# Optional local Marquez (OpenLineage API :5001, UI :3001)
./scripts/run-marquez.sh up

# Run a workflow in a Hop container
./scripts/run-hop.sh retail-example workflows/run-retail-initial.hwf
./scripts/run-hop.sh integration-tests tests/run-tests.hwf
----

After Marquez is up, export model-derived lineage with `retail-example/workflows/send-lineage-to-marquez.hwf` and open a link:hop-lineage-view.adoc[Hop Lineage View] (`.hlv`). Optional smoke: `./scripts/smoke-lineage-view.sh` (not part of `mvn test` or the multi-database suite). `${MARQUEZ_API}` is the export POST URL; `${MARQUEZ_BASE_URL}` is the Marquez host root used by the lineage backend.

See link:../scripts/README.md[scripts/README.md] and link:../integration-tests/PROJECT.md[integration-tests/PROJECT.md] for multi-database CI runs.

== Batch orchestration pattern

Typical production workflow chain:

1. **Harvest source metadata** — discover live source schemas, persist drift history (OPS); does not load the EDW (see link:metadata-harvesting.adoc[Metadata harvesting])
2. **Validate resource definitions** — schema gate / policy on contracts (optional axes: live, version, target DDL)
3. **Measure / evaluate source quality** — content rules (optional)
4. **Update resource definition group** (or dedicated DV / BV / DM update actions) — load the warehouse
5. Optional **Measure target quality** with alert-only disposition

Configure on each action:

* Pipeline run configuration (connection, logging, variables)
* **Parallel pipeline copies** — throughput vs resource use
* DDL options — execute on database, export to file, or fail if DDL needed (CI gate)
* Optional **catalog publish** after DV/BV updates

Retail example: `retail-example/workflows/run-retail-initial.hwf` and `run-retail-update.hwf`.

== Partial loads (record source groups)

Tag `DV_SOURCE` definitions with a **group** (for example `hourly`, `daily`). On **Data Vault Update**, set **Record source group** to load only matching sources. Empty group means all sources participate.

See link:datavault-source.adoc[Data Vault Source] and link:datavault-update-action.adoc[Data Vault Update action].

== Metrics and regression

The integration-tests project collects Data Vault / Business Vault update metrics JSON and runs golden-dataset unit tests. Use it as a reference for CI gates (model check abort, fail-if-DDL-needed).

=== Workflow load overview

**Preferred:** use the **Update resource definition group** workflow action. It loads every DV/BV/DM model listed on a resource definition group (order: all DV, then BV, then DM; list order within each layer), and can **manage vault update metrics** internally (assigns `DV_WORKFLOW_EXECUTION_ID` at start and publishes a load overview at the end). No separate Begin/End actions or hand-wired per-model hops are required.

image::images/update-resource-definition-group-action-dialog.png[Update resource definition group action dialog — group selection and layer includes,align="center"]

Full option reference: link:update-resource-definition-group-action.adoc[Update resource definition group action].

Retail example (`run-retail-update.hwf` / `run-retail-update-models.hwf`):

[source,text]
----
Harvest source metadata (optional Phase 1 wiring)
  → Schema gate (Validate resource definitions)
  → Measure / Evaluate source quality
  → Update resource definition group (retail-sources)
  → Advance load control
----

Metadata harvest details: link:metadata-harvesting.adoc[Metadata harvesting].

**Advanced:** you can still bracket custom multi-action graphs with:

1. **Begin Vault Update** — assigns `DV_WORKFLOW_EXECUTION_ID` (and `DV_WORKFLOW_EXECUTION_STARTED_AT`) before model updates run.
2. Per-model **Data Vault / Business Vault / Dimensional Update** actions (or a nested workflow).
3. **End Vault Update** — correlates all `load_run` rows with that execution id, publishes `workflow_load_overview` / `workflow_load_overview_model` to the OPS database, and optionally writes Markdown/HTML reports.

Schema gate details and HTML report samples: link:resource-definition-validation.adoc[Resource definition validation].

Configure the group action (or End Vault Update) with the same execution metrics profile as the model updates (`retail-execution-metrics`). Retail report files default to `${PROJECT_HOME}/work/reports`.

Catalog record definitions for ops tables are published under the FILE catalog storage root (retail: `work/edw-catalog/hop/<project>/operations/`) — for example `workflow_load_overview`, `workflow_load_overview_model`.

The HTML report summarizes the wave (model count, pipeline count, total duration, rows inserted) and lists each DV/BV/DM model with per-model duration and row counts:

image::images/workflow-load-overview-summary-models.png[Workflow load overview report — summary and per-model table for run-retail-initial,align="center"]

Drill into a model to see pipeline-level read, insert, error, and duration metrics:

image::images/workflow-load-overview-model-metrics.png[Workflow load overview — per-pipeline metrics for dimensional models,align="center"]

=== Load duration overview on model graphs

When an execution metrics profile is configured and prior runs are stored in the OPS database, DV/BV/DM model canvases can show a **Load durations** pane alongside the graph. Each model table gets a horizontal bar per recent run (Airflow-style), with hover tooltips for run time and status. Toggle the pane from the modeler toolbar; use **View data** to open catalog-backed load metrics.

image::images/data-vault-retail-360-model-with-duration-metrics.png[Retail 360 Data Vault model with load duration bars on the right,align="center"]

See link:plans/load-run-metrics-plan.md[load-run metrics plan] for the metadata contract and catalog schema.
