Why talk now

Users will notice two Hop Data Vault stories. Better we describe how they relate than let the market invent a rivalry.

1

Apache Hop users, Data Vault practitioners, and teams who want trusted history under analytics and AI.

2

3

Complementary jobs

A thin surface

How we work

How the Millersoft Engine works

A metadata-driven load factory: design in Studio, mapping workbook into PostgreSQL, generic Hop templates, staging, then raw vault.

Studio → Mapping workbook → pdi_meta → Generic Hop templates → Staging → Raw vault

Control plane

PostgreSQL holds design and run metadata. Staging is a first-class layer: business keys and hash columns are prepared there before vault loads.

Other databases

Vault tables can live in MySQL or SQL Server through PostgreSQL foreign data wrappers. Hop still talks to the Postgres gateway.

Studio is more than a drawing tool. It introspects sources, suggests hubs and links from keys, checks integrity, deploys DDL, and hands off to the Data Vault Hub to start and watch loads.

Notes. Credit the operational completeness: Hub, error tables, incremental staging, file loads. Ask what customers do after the raw vault — reports, BV, something else.

How we work

How hop-data-vault works

Visual models in git. A catalog as the contract bus. Generated pipelines. Consumption layers on the same spine.

.hsm source → Catalog → .hdv raw vault → .hbv Business Vault → .hdm dimensional

Design in files

Source, vault, Business Vault, and dimensional models are Hop files. Teams review them like code. The catalog stores source contracts and published target layouts as JSON.

Loads are generated

Workflow actions generate (or run) pipelines from the model. Staging is optional. Sources can be databases, CSV, Parquet, Iceberg, JSON, or other pipelines.

Targets are loaded natively — PostgreSQL, MySQL, SQL Server, SingleStore, Iceberg — rather than only through a Postgres gateway. Tables loaded by another engine can sit on the canvas as external and still feed Business Vault and dimensional models.

Notes. The external-table mode is the coexistence hook. Mention dbt import as proof hop-data-vault already on-ramps other metadata, not only its own.

Cooperation

Three ways to cooperate

Cheapest first. We can pick one. We do not need all three.

Coexistence — no shared runtime

Millersoft keeps loading the raw vault. hop-data-vault documents those tables as external on a Data Vault model and builds Business Vault and dimensional models on top. This mode already exists in the plugin. Millersoft does not have to change a line of Engine code.

Interchange — shared design, two engines

A design can be expressed in a small set of files (source model, catalog sources, raw vault model). Studio could export them; hop-data-vault can import them. Each engine still loads the way it does today.

On-ramp — Millersoft mapping into a Hop project

hop-data-vault reads the mapping workbook (and optionally metadata tables) and creates source + vault files. Same idea as the existing dbt → Business Vault importer. Useful for teams who start in Studio and later want file-based models.

Suggested starting point. Coexistence is available now. On-ramp (A1) is the first piece of new work. Interchange grows out of that if both sides like the file shapes.
Notes. Pause here. Ask which pattern Calum would actually want his users to see on a website. If “none yet,” A5 (publish schemas) is still a low-cost courtesy.

Cooperation

What we should not rush

Honesty about the large ideas, so they do not sit unspoken in the room.

✕

One merged engine

Replacing generic templates with generated pipelines — or the reverse — is a rewrite of someone’s runtime. It would freeze both roadmaps.

✕

One merged GUI

Studio is the Engine companion. Hop GUI and Hop Web are the plugin companion. Forcing one UI onto both metadata stores helps neither user.

✕

One shared Postgres catalog

That would pick Millersoft’s control plane as the standard. hop-data-vault’s file catalog would have to become a facade. Too early, too one-sided.

Not a rejection — a sequencing choice. If coexistence and interchange work, a closer runtime can be discussed later. Starting with a merge would spend the goodwill on plumbing.
Notes. If Calum hoped hop-data-vault would become the Engine behind Studio, say that is possible only after interchange exists — and it would still be their product decision.

The ask

Work hop-data-vault is willing to do

Five bounded items on the plugin side. Not a takeover. A1 is the start-here experiment.

A1 · Start here

Millersoft mapping importer

Read the Studio mapping workbook — and optionally metadata tables — into a source model, catalog sources, and a raw vault model.

Same shape as the existing dbt importer. Golden test: Sakila plus the published mapping spreadsheet. Millersoft does not have to change the Engine for this to be useful.

A5 · Shared offer

Publish the interchange schemas

Version the existing XSD and JSON Schema pack as a small “Hop EDW interchange” so both sides can emit or consume it.

An invitation to review — not a request to adopt blindly.

A2

Wizard UX inspired by Studio

Column pick, source profiling, and an integrity checklist on Generate Data Vault — so hop-data-vault learns from Studio’s guided flow without copying the application.

A3

Hop Web modelers

Keep investing in browser modelling on the same files as desktop. Complements Studio. Studio remains the Engine companion.

A4

Operations hub

A run view over hop-data-vault load metrics. Studio’s Data Vault Hub already proved this is what operators want. Credit where it is due.

What this is not

It is not a request that Millersoft rewrite the Engine, open a joint repo, or put hop-data-vault inside Docker Compose. A2–A4 happen on the plugin whether or not we share a brand.

Notes. Spend time here. Ask: is A1 welcome, awkward, or competing with a Studio export Calum already wants? If A1 is unwelcome, fall back to A5 plus coexistence.

Cooperation

Honest technical topics

Two differences that matter before anyone writes a single shared loader. They do not block coexistence or an importer.

How hash keys are made

Millersoft prepares SHA-256 hashes in staging (binary columns on the staged table). hop-data-vault computes hashes in the load pipeline, with a configurable algorithm and string representation.

An importer can either recompute (clean hop-data-vault loads) or treat staging as the source (preserve bits, keep a staging dependency). That is a joint call, not a surprise in production.

Staging as a product layer

For Millersoft, staging is required and hashed. For hop-data-vault, staging is optional: the catalog source may be the operational table, a file, or Iceberg.

Coexistence respects both. A single loader would have to pick. We should not pretend otherwise.

Also worth naming, later: status and validity satellites, multi-active keys, tenant columns, and error tables. Names differ; the intent often matches. An importer can map what is clear and report the rest.
Notes. Prefer recompute unless they have a regulatory reason to keep byte-identical hashes. Do not debate SHA-256 vs MD5 in the room unless they bring it up.

What success looks like from this conversation

A good meeting ends with a small, named next step — or with an honest “not now.”

1

A preferred pattern

Coexistence, interchange, on-ramp — or none of those yet. Written down in an email so neither of us reconstructs it later.

2

A yes, no, or later on A1

If the mapping importer would confuse Millersoft users, we will not ship it as a “Millersoft” brand without talking.

3

A reviewer for A5

Someone on the Millersoft side who can glance at the file schemas when they are versioned — even if Studio never emits them.

4

A channel

A lightweight way to stay in touch: GitHub issues, mail, or a periodic call. No steering committee required.

Also a success: agreeing that the products stay independent, point at each other kindly, and do not spend energy on a merged engine this year.
